# Configuration & Deployment Reference

Detailed configuration, feature-internals, and production deployment notes.
Moved out of the root `README.md` to keep that file a simple front door —
this is the deep reference. See also [PRODUCT-SPEC.md](PRODUCT-SPEC.md) for
the feature/product spec, and the `*-COMPLETION.md` files in this folder for
historical milestone-by-milestone implementation notes.

## AI Provider API Keys

Provider API keys (Anthropic, OpenAI) are server-side configuration only.
They are never accepted from, or returned to, the browser. There is no
provider-key settings page.

**Local development** — use .NET user-secrets from `src/WPAIPlugin.Api`:
```
dotnet user-secrets set "Planning:Anthropic:ApiKey" "<your-anthropic-key>"
dotnet user-secrets set "Planning:OpenAI:ApiKey" "<your-openai-key>"
```

Equivalent environment variables also work:
```
Planning__Anthropic__ApiKey=<your-anthropic-key>
Planning__OpenAI__ApiKey=<your-openai-key>
```

**Production** — set the key via your hosting platform's own server-side
secret/environment-variable facility. No secret manager integration exists
in this codebase yet.

## Authenticated Plugin Projects

Logged-in users plan/build through the SaaS UI (`/builder.html`), and builds
are saved to their account:

- `POST /api/plugins/plan` requires authentication. Legacy build routes are Development-only.
- `POST /api/projects/build` (authenticated) builds, optionally validates, and
  saves a project + version 1 for the current user.
- `GET /api/projects`, `GET /api/projects/{id}`, and
  `GET /api/projects/{id}/versions/{id}/download` are authenticated and scoped
  to the current user only.

**Development tooling only:** `POST /api/plugins/build` remains available to
`scripts/Validate-GeneratedPlugin.ps1` in Development. Both it and the legacy
`POST /api/plugins/build-validated` route are absent outside Development.
Customer builds use `/api/projects/build` exclusively.

Generated ZIPs are stored on the local filesystem under
`src/WPAIPlugin.Api/App_Data/artifacts/<user-id>/<project-id>/<version-id>/plugin.zip`
(configurable via `Artifacts:RootPath`), outside `wwwroot` and never served by
static-file middleware — downloads always go through the authenticated,
ownership-checked download endpoint. That directory is gitignored.

**Apply the EF migration to your local database:**
```
dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api
```

## Generated Plugin Validation

Proves a plugin generated by the deterministic `PluginBuilder` can actually be
installed and activated in a real WordPress site, not just pass unit tests.

**Requires:** Docker Desktop (running), PowerShell 7+.

**Run:**

```
powershell -ExecutionPolicy Bypass -File scripts/Validate-GeneratedPlugin.ps1
```

**Expected output on success:**

```
[1/5] Starting API
[2/5] Building plugin
[3/5] Starting WordPress
[4/5] Validating plugin
[5/5] Cleaning up
PASS: Plugin installed and activated successfully.
```

**What it checks:**
- Builds and starts the existing API, POSTs a deterministic `PluginSpec`
  (exercising shortcode, custom-post-type, settings-page, custom-fields, and
  scheduled-task) to the existing `POST /api/plugins/build` endpoint
- Starts a disposable MariaDB + WordPress + WP-CLI environment via Docker Compose
- `php -l` lints every generated PHP file before anything else runs
- Installs WordPress non-interactively, then `wp plugin install` +
  `wp plugin activate` + `wp plugin is-active` against the generated ZIP
- Fails immediately, with the exact command and exit code, if any step fails

**Cleanup:** the Docker containers, network, and volume are always torn down
(`docker compose down -v --remove-orphans`) and the API process is stopped in
a `finally` block, even if validation fails — nothing is left running.

This script is a manual/CI integration check. It requires Docker and is not
part of `dotnet test`, which remains Docker-independent.

## Manual WordPress Development Site

A persistent local WordPress install for manually testing WPAIPlugin-generated
ZIPs through the real wp-admin UI. Separate from, and independent of, the
disposable validation environment above — different project name, volumes,
and port. No WordPress setup or plugin installation is automated.

**Start:**
```
.\scripts\Start-WordPressDev.ps1
```

**Open:**
```
http://127.0.0.1:18437
```

**Stop** (preserves the site):
```
.\scripts\Stop-WordPressDev.ps1
```

**Reset completely** (run manually — deletes the database and all files):
```
docker compose -f docker/docker-compose.dev.yml down -v
```
WARNING: This completely deletes the local WordPress site and database.

**Manual plugin installation:**
1. Build/download a ZIP from WPAIPlugin (`Build Plugin` in the UI, or `POST /api/plugins/build`).
2. In WordPress: **Plugins → Add Plugin**.
3. **Upload Plugin**.
4. Select the ZIP.
5. **Install Now**.
6. **Activate**.

## Credit System

Authenticated customer builds use `POST /api/projects/build`. Costs come only
from server configuration: `Credits:SignupGrant`, `StandardBuildCost = 1`,
`ValidatedBuildCost = 2`. Planning costs zero. Unknown client cost fields are
ignored. `GET /api/credits` returns only the signed-in user's balance and the
two configured costs; there is no credit modification or history endpoint.

New registration creates Identity user, credit account and signup ledger entry
in one PostgreSQL transaction. Runtime missing-account reads return zero and
never grant credits. No credit fields were added to Identity, projects or
versions.

`CreditAccounts.Version` is an application-managed concurrency token with three
attempts. Each balance change and matching immutable ledger entry share a
SaveChanges unit. Refund retries recheck existing refunds and the original
charge. Refunds use a request-independent token, and failed pending project
writes are cleared first. A committed saved build remains charged even if the
client disconnects afterward. Refund exhaustion is an error, never silent success.
A process crash or database outage during compensation requires operational
reconciliation; durable background recovery is not implemented here.

The dashboard and builder fetch authoritative balances; JavaScript never
subtracts credits locally. Build labels use server costs, and balances refresh
after build/refund. No purchase controls or payment tables were introduced
outside of the Stripe integration described below.

`POST /api/plugins/build` is the anonymous **Development-only deterministic
validation path** used by `scripts/Validate-GeneratedPlugin.ps1`. It does not
consume credits and is absent in Production. The pre-existing authenticated
`/api/plugins/build-validated` route is also Development-only. The only
production customer build path is authenticated `POST /api/projects/build`.
No static customer UI calls either legacy path.

Apply migrations using the established command above, with the Development
configuration for the local database. Do not reverse a spent backfill or
reset the database; prefer a forward fix.

Normal `dotnet test` requires no PostgreSQL, Docker or OpenAI. The concurrent
charge/refund tests use separate InMemory contexts and a save barrier.

## Pre-payments security

Production (and Staging/non-Development) does not map either legacy build
endpoint. Never deploy a customer-facing instance with the Development
hosting environment. The local validation script explicitly sets Development.

| Route | Production access | CSRF | Rate limit |
| --- | --- | --- | --- |
| POST /api/plugins/build | Not mapped (404) | N/A | N/A |
| POST /api/plugins/build-validated | Not mapped (404) | N/A | N/A |
| POST /api/plugins/plan | Authenticated | Required | 10/user/minute |
| POST /api/projects/build | Authenticated; costs 1 or 2 credits | Required | 6/user/minute; validated additionally 2/user/minute |
| GET /api/projects and /api/projects/{id} | Authenticated, own records | Safe GET | None |
| GET /api/projects/{id}/versions/{id}/download | Authenticated, own artifact | Safe GET | None |
| GET /api/credits | Authenticated, own balance/costs only | Safe GET | None |
| POST /api/account/register and /login | Public | Required | Combined 10/IP/5 minutes |
| POST /api/account/logout | Public, clears caller session | Required | None |
| GET /api/account/me | Authenticated | Safe GET | None |
| GET /api/account/csrf | Public, no-store token bootstrap | Safe GET | None |
| POST /api/payments/checkout | Authenticated; PackId only, price/currency server-resolved | Required | 6/user/minute |
| POST /api/payments/webhook | Anonymous; Stripe signature required | N/A (signature is the control) | None (Stripe's own delivery/retry cadence) |
| GET /api/payments/history | Authenticated, own purchases only | Safe GET | None |
| /api/admin/* | Authenticated + Admin role (401/403 otherwise) | Required on mutating routes | None |
| Static UI | Public | N/A | None |

Rate limits are built-in ASP.NET fixed-window limiters, configured in the
`Security` section of appsettings.json. No queue or distributed store. User
partitions use the authenticated Identity ID, never browser-supplied IDs.
Validated requests take both build and validated permits before credits or
Docker work. Exhaustion returns 429 with Retry-After. Limits reset on restart
and apply per process. Login/register partitions use the connection IP; a
reverse-proxy deployment must deliberately configure trusted forwarding before
relying on individual client IPs. No untrusted forwarded headers are enabled.

JSON body limits: account endpoints 16 KiB, planning 64 KiB, builds 1 MiB;
Kestrel ceiling 1 MiB. Planner description maximum remains 2,000 characters.
Oversized requests return 413 in Production. Model/spec validation is retained.

The browser's `api.js` helper fetches a standard ASP.NET antiforgery request
token from GET /api/account/csrf before each POST and sends X-CSRF-TOKEN. The
paired antiforgery cookie remains HttpOnly. MVC validates registration, login,
logout, planning and builds. Fetching a new token handles identity transitions
without storing tokens in localStorage. Clients and local integrations using
SaaS routes must follow this exchange; the Development-only anonymous harness
build is intentionally exempt.

Identity cookies remain HttpOnly, SameSite=Lax, and Secure=Always outside
Development; local HTTP Development uses SameAsRequest. Antiforgery cookies use
SameSite=Strict with the same Secure policy. Production needs HTTPS. HSTS is
enabled outside Development. No JWT or CORS relaxation.

UI headers: nosniff, strict-origin-when-cross-origin referrer policy, DENY frame
protection and CSP with self-only scripts/connections, no objects/base URI/
framing, and same-origin forms. Inline page scripts were extracted into .js
files. Existing inline CSS is retained via style-src unsafe-inline. Only
Development Swagger permits inline scripts for its own bootstrap. API
responses are no-store. Downloads retain attachment Content-Disposition and
ownership checks; artifact roots beneath wwwroot are rejected at startup.

Outside Development, startup requires a nonempty database connection, selected
OpenAI or Anthropic provider key, and artifact root. Only the selected provider
is required; values are never included in startup validation errors. Runtime
production errors are generic; provider exception messages are not returned or
logged by our provider boundaries. Built-in oversized-body status is preserved.

No JWT or CORS relaxation, no schema-breaking changes to any of the above.

## Credit Purchases / Stripe

Authenticated customers can buy credit packs through Stripe Checkout
(`/billing.html`). The browser only ever sends a `PackId` — price, currency,
and credit amount are always resolved server-side from `CreditPacks:Packs`
configuration and never trusted from the request body.

**Configured credit packs** (GBP, integer pence — `999` = £9.99):

| PackId | Credits | Price |
| --- | --- | --- |
| `starter` | 25 | £4.99 |
| `builder` | 75 | £9.99 |
| `pro` | 200 | £19.99 |

GBP is the only supported currency at this time.

**Stripe configuration** — set via .NET user-secrets locally, or your
platform's environment-variable/secret facility in production. Never commit
real values:
```
dotnet user-secrets set "Stripe:SecretKey" "<your-stripe-secret-key>"
dotnet user-secrets set "Stripe:WebhookSecret" "<your-stripe-webhook-signing-secret>"
dotnet user-secrets set "Stripe:PublicBaseUrl" "https://your-app-domain"
```
Equivalent environment variables: `Stripe__SecretKey`, `Stripe__WebhookSecret`,
`Stripe__PublicBaseUrl`. `PublicBaseUrl` is used only to build the Checkout
success/cancel redirect URLs — it is never sent to the browser as
configuration. If `Stripe:SecretKey` or `Stripe:PublicBaseUrl` is blank,
`POST /api/payments/checkout` returns `503` cleanly rather than crashing —
credit purchases are an optional feature, not a hard startup requirement.

**Webhook endpoint**: `POST /api/payments/webhook`. Configure this URL in
your Stripe Dashboard (or via `stripe listen --forward-to
<your-url>/api/payments/webhook` for local testing) and set
`Stripe:WebhookSecret` to the signing secret Stripe gives you. Every request
is rejected with `400` unless its `Stripe-Signature` header verifies against
that secret — this is the only code path that can ever grant purchase
credits. The browser's success/cancel redirect never grants credits by
itself; it only re-reads the authoritative server balance.

**Idempotency**: every Stripe event ID is recorded in `ProcessedPaymentEvents`
before being acted on, so a retried webhook delivery is a safe no-op. Credits
are granted through the existing ledger-backed `CreditService`
(`CreditTransactionType.CreditPurchase`), keyed by the `Purchase.Id` — a
duplicate grant attempt for an already-completed purchase is also a no-op.

**Refunds**: this system does not implement automatic customer-initiated
refunds. A Stripe monetary refund is recorded against the local `Purchase`
row (`RefundedAmountMinor`) for admin visibility only — it never automatically
reduces the customer's credit balance, since that could take a balance
negative or claw back credits already spent. Any credit correction associated
with a refund must be made as a separate, explicit, audited admin credit
adjustment (`/admin` → Users → a customer's Adjust Credits form).

**Signup grant**: a small number of free credits (`Credits:SignupGrant` in
`appsettings.json`) so a new user can try the service before purchasing.

**Admin revenue/analytics**: `/admin` → **Revenue** shows gross/net revenue,
refunds, successful/failed purchases, credits sold, purchasing customers,
average purchase, and a day-by-day breakdown — all sourced from `Purchase`
records, never from the credit ledger. The same tab also shows an
"Approximate contribution estimate" (revenue vs. estimated AI spend, kept in
their separate native units, explicitly never called profit) and operational
analytics with Today / 7 days / 30 days / This month / All time filters.

Verification and evidence (including real Stripe test-mode checks):
[STRIPE-FINANCIAL-COMPLETION.md](STRIPE-FINANCIAL-COMPLETION.md).

### Stripe live-mode activation (owner-only)

Everything above runs in Stripe **test mode** until an owner deliberately
switches over. Nothing in this codebase assumes test vs. live — Stripe
itself distinguishes `sk_test_...`/`sk_live_...` keys and test/live webhook
signing secrets; the app just reads whatever `Stripe:SecretKey` and
`Stripe:WebhookSecret` are configured. Switching to live mode is entirely a
configuration change, made by whoever owns the Stripe account:

1. **Create/configure the Stripe live account** — complete Stripe's own
   account activation (business details, bank account for payouts) in the
   Stripe Dashboard. Nothing in this repository does this for you.
2. **Obtain the live secret key** — Dashboard → Developers → API keys →
   reveal the live `sk_live_...` secret key. Never paste it into a repo
   file; set it only via your production host's environment-variable/secret
   facility as `Stripe__SecretKey`.
3. **Configure a production webhook endpoint** — Dashboard → Developers →
   Webhooks → Add endpoint → URL `https://<your-domain>/api/payments/webhook`
   (see "Stripe webhook — production route" below), events at minimum
   `checkout.session.completed`, `checkout.session.expired`,
   `payment_intent.payment_failed`.
4. **Obtain the live webhook signing secret** — shown once the endpoint is
   created (Dashboard → that endpoint → "Signing secret"). Set it as
   `Stripe__WebhookSecret` alongside the secret key.
5. **Configure both secrets, plus `Stripe__PublicBaseUrl`** (your real
   `https://` domain, used to build the Checkout success/cancel redirect —
   see "Domain / HTTPS / reverse proxy" below), in the production
   environment only — never in a committed file.
6. **Verify the configured GBP packs** (`CreditPacks:Packs`) still reflect
   the prices the owner wants to charge for real money before going live;
   change `appsettings.json`/environment overrides first if not.
7. **Perform exactly one controlled live transaction**, using a real card,
   only after the owner has explicitly decided to launch — confirm the
   Checkout session completes, the webhook is received and verified, credits
   are granted exactly once, and the purchase appears correctly in `/admin`
   → Revenue. **This step is owner-executed; it is not performed by an
   automated agent or this codebase.**

No code change is required for any of the above — `POST /api/payments/checkout`
already returns a clean `503` if `Stripe:SecretKey`/`Stripe:PublicBaseUrl` are
blank, so the feature simply activates the moment real values are configured.

### Stripe webhook — production route

`POST /api/payments/webhook` is the only production webhook route; there is
no separate test/live path. It is deliberately:

- **Unauthenticated** (`[AllowAnonymous]`) — Stripe cannot present a login
  session or CSRF token, so authentication is not the control here.
- **Signature-required** — every request is rejected `400` unless
  `Stripe-Signature` verifies against `Stripe:WebhookSecret` via the real
  `Stripe.net EventUtility.ConstructEvent` call; a missing or malformed
  signature is handled the same way (bare `400`, payload/signature never
  echoed back).
- **Retry-safe** — Stripe's own retry/backoff redelivers on non-2xx; a
  retried delivery of an already-processed event ID is a no-op via
  `ProcessedPaymentEvents`, and a second `checkout.session.completed` for an
  already-`Completed` purchase is independently blocked at the
  business-status level — double protection, so out-of-order or duplicate
  delivery can never double-grant.
- **Session-independent** — reads only the raw request body and the
  `Stripe-Signature` header; never touches cookies or ASP.NET Core session
  state.
- **Secret-safe** — no log statement on this path ever includes the webhook
  secret, the raw payload, or the signature; failures log only a category
  (`ex.GetType().Name`).

If your reverse proxy buffers, rewrites, or re-encodes the request body
before it reaches Kestrel, Stripe's signature check will fail (the signature
is computed over the exact raw bytes Stripe sent) — configure the proxy to
pass this route's body through unmodified, same as any standard Stripe
integration.

## Free builds + promotions

Every new registration receives two benefits, granted once, in the same
transaction as the Identity account itself:

- **Signup credits** (`Credits:SignupGrant`).
- **Free plugin builds** (`Promotions:SignupFreeBuilds`) — a separate
  entitlement, never converted to or from credits, tracked in its own
  ledger-backed `BuildEntitlementAccount`/`BuildEntitlementTransaction`
  tables (the same application-managed-concurrency, immutable-ledger design
  `CreditService` already uses for credits).

**How free builds and credits interact** at build time — the server always
decides, never the browser:

| | Standard Build | Build & Validate |
| --- | --- | --- |
| Free build available | 0 credits | 1 credit (validation only) |
| No free build available | 1 credit (configured `StandardBuildCost`) | 2 credits (configured `ValidatedBuildCost`) |

A single `build:<guid>` reference correlates the credit charge and the
free-build consumption for one build attempt, so a failed build after
charging refunds exactly what was actually consumed. `GET /api/credits`
returns both `balance` and `freeBuildsRemaining` together; the Builder and
Dashboard pages show both without decrementing either client-side, always
re-fetching after a build/refund.

**Existing accounts get 0 free builds** unless explicitly granted — this
offer applies to new registrations, not retroactively. A missing
`BuildEntitlementAccount` row simply reads as 0. An admin can grant free
builds to specific existing users via a `FreeBuilds`-type promotion
redemption (see below) — never automatically at startup or login.

### Promotions system

A small, generic `Promotion` model supports three types:

- **`FreeBuilds`** — grants a free-build entitlement. Always requires a
  code (redeemed immediately via `POST /api/promotions/redeem { code }`,
  independent of any pack/Checkout).
- **`BonusCredits`** — an extra, separately-tracked credit grant on top of
  a pack purchase (ledger type `PromotionBonus`, never merged into
  `CreditPurchase` — admin reporting always distinguishes purchased vs.
  promotional credits).
- **`PackPriceDiscount`** — a whole-number percentage (1–100) off a pack's
  price, computed server-side in `decimal` (never `float`/`double`),
  rounded to the nearest whole minor currency unit with `.5` rounding away
  from zero. Example: Builder £9.99 (999p) at 25% → 999 × 0.25 = 249.75 →
  rounds to 250p discount → **£7.49 (749p) paid**.

Each promotion has a server-computed state (`Draft`/`Scheduled`/`Active`/
`Expired`, derived from `IsEnabled`/`StartsAtUtc`/`EndsAtUtc` against the
current UTC time — never stored, never dependent on browser time), optional
`Code` (case-insensitive, normalized to uppercase), optional pack scoping
(`AppliesToPackId`, null = all packs), an `Eligibility` axis (`Everyone`,
`FirstPurchaseOnly`, or `NewRegistrations`), and optional
`MaxRedemptions`/`MaxRedemptionsPerUser` limits.

**No stacking**: at most one promotion applies per purchase. An explicit,
valid promo code always wins over any automatic (no-code) deal. Among
multiple eligible automatic promotions, the highest `Priority` wins; ties
break by `CreatedAtUtc` then `Id` — deterministic, never ambiguous.
`GET /api/payments/packs` shows each pack's currently-resolved automatic
pricing so the billing page can display an active deal without a code;
`POST /api/promotions/resolve-code` previews a specific code's terms before
checkout is created; `POST /api/payments/checkout` accepts an optional
`PromoCode` and does the real, final resolution.

**Checkout snapshot**: the resolved terms (base price, paid price, base
credits, bonus credits, and the promotion's own id/code/name) are written
onto the `Purchase` row the instant Checkout is created — never re-resolved
later. If the referenced promotion is edited, disabled, or expires before
the customer completes payment, the already-created Purchase's terms are
unaffected. The redemption limit (but never the price/credits already
agreed) is re-checked once more at webhook-completion time.

**Stripe interaction**: the browser never sets a discount, bonus, or final
price; Stripe only ever sees the already-resolved amount; credits (base and
bonus) are granted exclusively by the verified webhook, never the success
redirect.

**Admin**: `/admin` → **Promotions** — create/edit/enable/disable/duplicate
(no hard delete, ever — once redemptions exist, a promotion can only be
disabled/archived) and per-promotion reporting (redemptions, purchasing
customers, credits/free-builds granted, discount amount, associated
revenue). Every mutation is `AdminOnly`-gated, CSRF-protected, and produces
an `AdminAuditLog` entry.

**Rate limiting**: `POST /api/promotions/resolve-code` and
`POST /api/promotions/redeem` share a dedicated `promoCode` policy
(`Security:PromoCodePerMinute`, default 10/user/minute).

**A known, accepted limitation**: `MaxRedemptions`/`MaxRedemptionsPerUser`
are enforced by counting existing `PromotionRedemption` rows at
resolution/completion time, not by a database-level constraint. Under a
genuine simultaneous double-submission, a redemption limit could in theory
be exceeded by one — a deliberate, documented tradeoff, not the
credit/free-build concurrency guarantee itself (that one remains airtight).

## Password recovery / transactional email

`/forgot-password.html` and `/reset-password.html`, linked from the login
page. Uses ASP.NET Core Identity's own reset-token mechanism throughout —
no custom token crypto, no reset-token database table, no raw token ever
persisted.

**Flow**: a customer submits their email to `POST /api/account/forgot-password`.
Whether or not that email belongs to a registered account, the response is
always the identical `"If an account exists for that email address, a
password reset link has been sent."` — the endpoint never reveals account
existence, lockout status, or any other account state through a response
difference. Only for a real, matching account does anything happen
server-side: `UserManager.GeneratePasswordResetTokenAsync` issues a token,
and a reset URL is built **exclusively** from `App:PublicBaseUrl` — request
Host/scheme/Origin headers are never trusted for this, so a spoofed Host
header cannot redirect a real reset link to a hostile domain. The customer
then submits a new password (with confirmation) plus that email/token to
`POST /api/account/reset-password`, which validates the token via
`UserManager.ResetPasswordAsync` and applies the existing Identity password
policy — no separate/conflicting client-side policy.

**Token lifetime**: 1 hour (`DataProtectionTokenProviderOptions.TokenLifespan`,
configured explicitly in `Program.cs`) — shorter than ASP.NET Core Identity's
own 1-day default, since a password-reset link is more sensitive than the
confirmation-email tokens that default was designed for.

**Rate limiting**: a dedicated `passwordRecovery` policy (see
`Security:PasswordRecoveryPerFiveMinutes`, default 5 per 5 minutes),
partitioned by client IP (not by user). Applies to both `forgot-password`
and `reset-password`. CSRF protection is unchanged.

**Never logged**: the reset token, the complete reset URL, the password, or
the security stamp. A send failure is logged only as a safe category string
and never changes the response shape.

**Transactional email** — `ITransactionalEmailSender` (`src/WPAIPlugin.Api/Email/`)
is a small seam, mirroring the existing `IPaymentGateway`/`IPlanningProvider`
pattern: `ResendTransactionalEmailSender` is the only file that references
the Resend SDK directly, and is selected in DI only when `Resend:ApiKey` is
configured. When it isn't (Development, or any deployment that hasn't opted
in), `NoOpTransactionalEmailSender` is used instead — it never sends
anything and never logs the token/URL, only a fixed safe line. Outside
Development, `Resend:ApiKey` (along with `App:PublicBaseUrl`, `Support:Email`,
`Email:FromAddress`, `Email:FromName`) is a hard startup requirement (see
"Required environment variables" below) — password reset is core
account-security, not an optional feature like Stripe. Tests use their own
`FakeTransactionalEmailSender`, recording the recipient/reset URL for
inspection — never Resend, never the internet.

Email content is transactional only (currently: the password-reset email,
subject "Reset your ModuleMint password") — no newsletters, marketing
campaigns, mailing lists, or promotional automation exist or are planned.

**Configuration**:
```
dotnet user-secrets set "App:PublicBaseUrl" "https://your-app-domain"
dotnet user-secrets set "Support:Email" "support@your-domain"
dotnet user-secrets set "Email:FromAddress" "no-reply@your-domain"
dotnet user-secrets set "Email:FromName" "ModuleMint"
dotnet user-secrets set "Resend:ApiKey" "<your-resend-api-key>"
```
Equivalent environment variables: `App__PublicBaseUrl`, `Support__Email`,
`Email__FromAddress`, `Email__FromName`, `Resend__ApiKey`. See
[.env.example](../.env.example).

## Legal pages / Support

`/privacy.html`, `/terms.html`, `/refunds.html`, `/support.html` — static
pages in the same ModuleMint dark/mint styling as the rest of the site,
linked from the public homepage footer, the billing page, and (Support)
from the login/forgot-password flow. `GET /api/config/public` (anonymous)
exposes the one non-secret value these pages need — the configured support
email — never anything secret-shaped.

**These pages describe only real, current application behaviour** — they do
not invent legal wording, guarantees, or company details. Every page
carries a visible, explicit notice that the following remain owner-supplied
launch blockers, not yet confirmed:

- **Legal operator identity** — currently the literal placeholder
  `[LEGAL OPERATOR NAME]`. Real trading name / registered company details
  are required before launch.
- **Governing jurisdiction** — currently a working assumption (Scotland),
  flagged for explicit owner/legal confirmation.
- **Production domain**, **real support email/domain**, **business/registered
  address**, **company registration number**, and **VAT details** (if
  applicable) — none of these are fabricated; `Support:Email`/`App:PublicBaseUrl`

## Public homepage

# Production Deployment

## Prerequisites

- A PostgreSQL 17 (or compatible) server, reachable from the app.
- An OpenAI or Anthropic API key for the one provider you select via
  `Planning:DefaultProvider`.
- HTTPS termination in front of the app (see "Reverse proxy / HTTPS" below).
- Optional: Docker available to the app's host if you want `Build &
  Validate` (see "Docker validation in production" below) - standard
  builds never need it.
- .NET 8 runtime (via the provided Docker image, or installed directly).

## Required environment variables

All configuration binds from environment variables using ASP.NET Core's
double-underscore convention (`Section__Key`), or from your platform's own
secret facility. See [.env.example](../.env.example) for the full list. At
minimum, production (`ASPNETCORE_ENVIRONMENT=Production` or any non-
Development environment) refuses to start without:

| Variable | Purpose |
| --- | --- |
| `ConnectionStrings__DefaultConnection` | PostgreSQL connection string |
| `Planning__DefaultProvider` | `openai` or `anthropic` |
| `Planning__OpenAI__ApiKey` or `Planning__Anthropic__ApiKey` | Whichever provider is selected |
| `Artifacts__RootPath` | Where generated ZIPs are stored (must be outside `wwwroot`; startup also verifies this) |
| `App__PublicBaseUrl` | Absolute production URL, used to build password-reset links — never a browser-supplied Host header |
| `Support__Email` | Shown on the Support page and used for privacy/billing/refund/account-access enquiries |
| `Email__FromAddress` and `Email__FromName` | The From identity on every transactional email |
| `Resend__ApiKey` | Sends the password-reset email — see "Password recovery / transactional email" above |

This check exists at the top of `Program.cs` and throws
`InvalidOperationException` with a generic message (never the missing
value) if any of these are blank outside Development. Password reset is a
core account-security feature, not an optional one like Stripe, so
production never silently falls back to the no-op email sender.

Everything else (`Credits:*`, `Security:*`, `Validation:*`,
`DataProtection:KeyRingPath`, `ForwardedHeaders:*`, `Stripe:*`,
`CreditPacks:*`) has a safe default from `appsettings.json` and is optional
to override. `Stripe:SecretKey` and `Stripe:PublicBaseUrl` are not
startup-required — credit purchases simply return `503` until configured.

## Database migrations

Migrations are **not** applied automatically on startup - `Program.cs`
never calls `Database.Migrate()`. Apply them as an explicit deployment
step, before starting a new version of the app against the database:

```
dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api --connection "<production connection string>"
```

or, from a machine that already has the target connection string in its
own configuration/environment, omit `--connection` and let it read
`ConnectionStrings:DefaultConnection` normally. Each migration is additive
(new tables/columns only, no existing table rewritten) and incremental -
never regenerate or edit an existing migration; add a new one instead.

**Using `docker-compose.prod.example.yml`**: the `db` service is
deliberately not published on a host port, so you need a machine/container
that can reach it on the compose network. From a checkout with the .NET 8
SDK and the `dotnet-ef` tool installed (`dotnet tool install --global
dotnet-ef`), on the same Docker network as the `db` service:
```
dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api --connection "Host=db;Port=5432;Database=<POSTGRES_DB>;Username=<POSTGRES_USER>;Password=<POSTGRES_PASSWORD>"
```
Or run it from a throwaway container built from this repo's own build
stage, attached to the compose project's network (`<project-name>_default`):
```
docker build --target build -t wpaiplugin-api:build-stage .
docker run --rm --network <project-name>_default \
  -e ConnectionStrings__DefaultConnection="Host=db;Port=5432;Database=<POSTGRES_DB>;Username=<POSTGRES_USER>;Password=<POSTGRES_PASSWORD>" \
  wpaiplugin-api:build-stage \
  bash -c "dotnet tool install --global dotnet-ef --version 8.* && export PATH=\"\$PATH:/root/.dotnet/tools\" && dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api"
```
This whole flow (build → compose up → migrate via a build-stage container
→ verified the app serves real requests) was tested end-to-end against a
disposable compose project before this note was written.

## Admin bootstrap

Real ASP.NET Core Identity roles, not a hard-coded email — `Admin:BootstrapEmail`
(blank by default; set only via production configuration, never committed)
is the sole input. `AdminBootstrapper` runs once on every startup and:

- Does nothing if `Admin:BootstrapEmail` is blank.
- Does nothing if **any** user already holds the `Admin` role (never
  re-grants, never nominates a second account automatically).
- Grants `Admin` to the configured email **only if that account has already
  registered**; if it hasn't yet, does nothing this run and tries again on
  the next startup.

No admin information is ever exposed to unauthenticated or non-admin
requests — every `/api/admin/*` route requires the `Admin` role (401
anonymous, 403 non-admin), and `GET /api/account/me` only reports the
caller's own `isAdmin` flag.

**Operator steps, in order:**

1. **Deploy** the application with `Admin:BootstrapEmail` **unset** (or set
   to the intended owner's email from the start — both are safe, see below).
2. **Register the intended owner account** through the normal public
   `/register.html` flow, using the real email address that will become the
   administrator.
3. **Set `Admin:BootstrapEmail`** (if not already set) to that exact email
   in production configuration (environment variable
   `Admin__BootstrapEmail`, your platform secret store, etc.) and restart
   the application — the bootstrapper runs once per process start, so a
   restart is required for the grant to take effect after registration.
4. **Verify Admin access**: log in as that account (role claims are baked
   into the Identity auth cookie at sign-in, so a role granted mid-session
   only takes effect on the *next* login) and confirm `GET /api/account/me`
   reports `"isAdmin": true`, the "Admin" nav link appears, and `/admin`
   loads.
5. **Afterward**: leaving `Admin:BootstrapEmail` configured is safe and has
   no further effect once an admin exists, so there is no requirement to
   remove it.

There is no in-app endpoint to promote additional administrators — the
bootstrapper only ever acts while zero admins exist, and `AdminController`
has no role-granting route (by design: a self-service "make me admin"
surface would be a real privilege-escalation risk). Adding a second admin
today requires a direct, operator-performed database change (inserting the
existing `Admin` `AspNetRoles` row into `AspNetUserRoles` for the target
user's ID).

## Data Protection key persistence

ASP.NET Core Identity's auth cookies and the antiforgery (CSRF) tokens are
both protected using the Data Protection key ring. `Program.cs` persists
keys to a filesystem path (`DataProtection:KeyRingPath`, defaulting to
`App_Data/dataprotection-keys` next to artifact storage) via
`PersistKeysToFileSystem` - **that directory must be on a volume that
survives restarts/redeployment** (see the Docker image and compose example
below, which already mount it). If you run multiple app instances behind a
load balancer, they must share this same persisted directory (e.g. a
shared volume/NFS mount) or each instance will reject the others' cookies.

## Reverse proxy / HTTPS

The app expects TLS to terminate either directly at Kestrel or at a
reverse proxy (nginx, Caddy, Cloudflare, a cloud load balancer) in front
of it - no bundled reverse proxy.

`X-Forwarded-For`/`-Proto`/`-Host` are only honored from proxies you
explicitly list in `ForwardedHeaders:KnownProxies` (IP addresses) or
`ForwardedHeaders:KnownNetworks` (CIDR ranges, e.g. `172.16.0.0/12` for a
typical Docker bridge). With neither configured (the default), nothing is
forwarded and the app sees the connection exactly as Kestrel received it.
Configure this before relying on per-client-IP rate limiting or HTTPS-based
cookie security behind a proxy.

`UseHttpsRedirection` and `UseHsts` (outside Development) remain active.
Identity cookies stay `HttpOnly`, `SameSite=Lax`, `Secure=Always` outside
Development; antiforgery cookies stay `HttpOnly`, `SameSite=Strict`, same
Secure policy.

## Security headers

CSP (`default-src 'self'; script-src 'self'; ...`), plus
`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`,
`X-Frame-Options: DENY`, and `Permissions-Policy: camera=(), microphone=(),
geolocation=(), payment=()`. No `unsafe-inline`/`unsafe-eval` for scripts.

## Artifact storage

Generated plugin ZIPs live under `Artifacts:RootPath`
(`App_Data/artifacts` by default; `/app/App_Data/artifacts` in the Docker
image), addressed only by server-generated GUID path segments - never a
user-supplied name - so there is no path-traversal surface (see
`PluginArtifactStore.ResolvePath`). Startup refuses to run if this path
resolves inside `wwwroot`. **This directory must be a persistent volume**
in any container/redeploy setup, or every build a user has ever downloaded
is lost on the next deploy.

## Docker validation in production

`Build & Validate` (2 credits) shells out to the `docker` CLI
(`DockerPluginValidator`) to run a disposable WordPress environment via
`docker/docker-compose.validate.yml`. **Standard `Build Plugin` (1 credit)
never touches Docker.** If you want `Build & Validate` available in
production:

- The app's own container needs the host's Docker socket mounted
  (`/var/run/docker.sock`) and the `docker` CLI on `PATH` - the provided
  Dockerfile does not include the Docker CLI or mount the socket by
  default, since doing so grants the app container effective root on the
  host. Mount it only if you've accepted that tradeoff (see the commented-
  out line in `docker/docker-compose.prod.example.yml`).
- Each validation run uses a GUID-suffixed temp directory and compose
  project name, so concurrent validations never collide, and always
  removes containers/volumes/temp files in a `finally` block.
- If Docker is unavailable, `Build & Validate` fails cleanly with
  `ValidationUnavailable` and the credit charge is refunded.
- If you don't want to support `Build & Validate` in production at all,
  simply don't mount the socket; the button still exists but fails cleanly.

## Logging

Structured `ILogger` throughout (no third-party logging platform added).
Production suppresses the framework's own exception-message logging
because it includes the raw exception message, which could contain a
provider error body. `DockerPluginValidator` truncates command output
before logging it and never logs the generated plugin's source. No
passwords, cookies, API keys, connection-string passwords, or full user
prompts are ever logged.

## Health checks

`GET /health/live` - anonymous, no database access, confirms the process
is alive. Returns `200 Healthy` (plain text).

`GET /health/ready` - anonymous, additionally confirms PostgreSQL is
reachable via a plain `Database.CanConnectAsync()` check. Returns `200
Healthy` or `503 Unhealthy` (plain text) - never a connection string,
database name, or exception detail.

Point your orchestrator's liveness probe at `/health/live` and (if it
distinguishes the two) readiness probe at `/health/ready`.

## Error handling

Outside Development, unhandled exceptions return a generic
`{"error": "The request could not be completed. Please try again."}`
(500) or the correct status for a known `BadHttpRequestException` (e.g.
413 for an oversized body) - never a stack trace, SQL, EF details, Docker
internals, or provider secrets. Development keeps the full ASP.NET
developer exception page for debugging.

## Static files / cache

`UseStaticFiles`/`UseDefaultFiles` serve only `wwwroot` - artifact storage
is deliberately outside it and startup enforces that separation. API
responses (`/api/*`) are `Cache-Control: no-store`. No asset build
pipeline, fingerprinting, or bundler.

## Docker image

`Dockerfile` (repository root) is a two-stage build: `sdk:8.0` to restore
and `dotnet publish -c Release`, then `aspnet:8.0` for the runtime image
with only the published output copied in - no source tree, no SDK, no
build tools in the final image. Runs as the image's built-in non-root
`app` user. Listens on port 8080 (`ASPNETCORE_URLS=http://+:8080`, TLS
terminates at your reverse proxy - see above). `Artifacts__RootPath` and
`DataProtection__KeyRingPath` default to `/app/App_Data/...` inside the
image; mount volumes over both (see
`docker/docker-compose.prod.example.yml`) or their contents are lost on
every container replacement. Does not bundle PostgreSQL or Docker-in-
Docker.

Build it:
```
docker build -t wpaiplugin-api .
```

## Backup / restore

Two things need backing up, and they should be backed up **at roughly the
same time** so a restore doesn't reintroduce a project/version row whose
ZIP no longer exists (or vice versa):

1. **PostgreSQL database.**
   ```
   pg_dump -h <host> -U <user> -d <database> -F c -f wpaiplugin-backup.dump
   ```
   Restore:
   ```
   pg_restore -h <host> -U <user> -d <database> --clean --if-exists wpaiplugin-backup.dump
   ```
2. **Generated plugin artifacts** - the `Artifacts:RootPath` directory
   (`/app/App_Data/artifacts` in the Docker image, or the corresponding
   named volume). A plain recursive file copy/archive is sufficient.

Also preserve the **Data Protection key directory**
(`DataProtection:KeyRingPath`) in your backup/restore plan - restoring the
database and artifacts without it still forces every user to log in again
after a restore, which is safe but disruptive.

This is manual/scriptable guidance, not an automated backup framework -
schedule these however your platform normally schedules backups (cron,
your cloud provider's snapshot feature, etc.).

## Resource / disk considerations

Operational guidance only - no specific sizing is claimed without
measurement:

- **Generated ZIP storage** grows without bound as users build more
  plugins (every successful build keeps its ZIP; there is no automatic
  pruning). Monitor `Artifacts:RootPath` disk usage.
- **Temporary build/validation space**: `Build & Validate` writes to the
  OS temp directory for the lifetime of one validation run and always
  cleans up afterward.
- **Docker validation disk usage**: each `Build & Validate` run
  pulls/uses the `wordpress:php8.2-apache` and `mariadb:11` images
  (cached after first pull) and creates disposable containers/volumes.
- **PostgreSQL storage** grows with users, projects, versions, and the
  immutable credit-transaction ledger (append-only by design).
- **Log growth** depends entirely on your logging provider/sink
  configuration.

# Plesk + Docker Deployment

The concrete, current deployment target: a single existing Plesk server
with Docker available, hosting `https://modulemint.co.uk`. Plesk owns the
public domain, HTTPS, and the reverse proxy; Docker Compose owns the app
and its database. This section is written so another administrator can
follow it without reading the rest of this file first.

```
Internet
   ↓
https://modulemint.co.uk
   ↓
Plesk (HTTPS termination + reverse proxy)
   ↓
127.0.0.1:18473
   ↓
modulemint container (ASP.NET Core, port 8080 internally)
   ↓
postgres container (internal network only, no public port)
```

## Prerequisites

- Docker + Docker Compose available on the Plesk server.
- A checkout of this repository on the server (e.g. `git clone`, or however
  releases normally reach this host).
- Plesk configured to serve `https://modulemint.co.uk` (certificate,
  HTTP→HTTPS redirect) and able to reverse-proxy to a local port - see
  "Plesk reverse proxy configuration" below.
- Real production values ready for: PostgreSQL password, OpenAI API key,
  Resend API key, support/sender email addresses.

## Files involved

| File | Purpose |
| --- | --- |
| `Dockerfile` | Multi-stage build → the `modulemint` production image (same image used for local dev/testing of prod config). |
| `.dockerignore` | Keeps `.git`, dev secrets, tests, and docs out of the build context/image. |
| `docker/docker-compose.production.yml` | The two-service stack: `modulemint` + `postgres`. Committed - contains no secrets, only `${VAR}` references. |
| `.env.production.example` | Committed template. Copy to `.env.production` on the server and fill in real values. |
| `.env.production` | **Not committed** (gitignored). Real secrets live only here, on the server. |
| `scripts/Deploy-Production.sh` | Optional helper that runs the sequence below with a backup confirmation prompt. |

## First-time setup

1. **Clone the repository** onto the server, in whatever location you
   normally keep deployed apps.
2. **Create the environment file:**
   ```
   cp .env.production.example .env.production
   ```
   Edit `.env.production` and fill in: `POSTGRES_PASSWORD`,
   `OPENAI_API_KEY`, `RESEND_API_KEY`, `SUPPORT_EMAIL`,
   `EMAIL_FROM_ADDRESS`. Leave `APP_PUBLIC_BASE_URL` as
   `https://modulemint.co.uk` and `VALIDATION_ENABLED=false` (see
   "Why Build & Validate is off" below). Never commit this file.
3. **Build and start:**
   ```
   docker compose --env-file .env.production -f docker/docker-compose.production.yml -p modulemint up -d --build
   ```
   This starts `postgres` (waits for its healthcheck) then `modulemint`.
   PostgreSQL is not published on any host port - only `modulemint` can
   reach it, over the internal compose network as host `postgres`.
4. **Apply database migrations** - not automatic on startup by design (see
   "Database migrations" above). From the server, with the .NET 8 SDK
   available (or using the throwaway build-stage container shown there):
   ```
   docker build --target build -t modulemint-api:migrate .
   docker run --rm --network modulemint_default \
     -e ConnectionStrings__DefaultConnection="Host=postgres;Port=5432;Database=<POSTGRES_DB>;Username=<POSTGRES_USER>;Password=<POSTGRES_PASSWORD>" \
     modulemint-api:migrate \
     bash -c "dotnet tool install --global dotnet-ef --version 8.* && export PATH=\"\$PATH:/root/.dotnet/tools\" && dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api"
   ```
5. **Confirm the app is up**, from the server itself (this port is not
   reachable from outside the host):
   ```
   curl http://127.0.0.1:18473/health/ready
   ```
6. **Configure the Plesk reverse proxy** (below), then visit
   `https://modulemint.co.uk`.
7. **Register the intended admin account**, then set
   `ADMIN_BOOTSTRAP_EMAIL` in `.env.production` to that address and
   `docker compose ... up -d modulemint` (recreates just that service) to
   apply it - see "Admin bootstrap" above for the full mechanism.

`scripts/Deploy-Production.sh` automates steps 3-5 (build, migrate, start,
wait for health) with a backup-confirmation prompt - read it before first
use; it still requires `.env.production` to already exist.

## Plesk reverse proxy configuration

In the Plesk domain settings for `modulemint.co.uk`, under **Apache & nginx
Settings** (or the "Additional nginx directives" box, depending on Plesk
version), add a proxy pass to the local app port:

```
location / {
    proxy_pass http://127.0.0.1:18473;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $host;
}
```

(Exact UI labels vary by Plesk version - the goal is any config that proxies
`https://modulemint.co.uk` to `http://127.0.0.1:18473` and forwards those
three headers.) Enable **SSL/TLS support** with Let's Encrypt for the
domain, and Plesk's own **"Permanent SEO-safe 301 redirect from HTTP to
HTTPS"** option. If `www.modulemint.co.uk` is also pointed at this site,
configure Plesk's own redirect from `www` to the bare domain (or vice
versa) - pick one canonical form and redirect the other to it.

**Trusted-proxy configuration - read this before changing it.**
`docker-compose.production.yml` sets both `ForwardedHeaders__KnownProxies`
(`127.0.0.1`/`::1`) *and* `ForwardedHeaders__KnownNetworks__0`
(`172.28.90.0/24`, this compose project's own fixed bridge subnet - see the
`networks:` block at the bottom of that file). Both are needed: when Plesk
(running directly on the host, not in a container) connects to
`127.0.0.1:18473`, Docker's own NAT rewrites that connection's source
address by the time it reaches the container - verified locally, the
container sees the project's bridge gateway IP, **not** `127.0.0.1`. Trusting
only `KnownProxies: 127.0.0.1` therefore silently never matches, forwarded
headers are ignored, `Request.Scheme` stays `http`, and every
CSRF-protected POST (register, login, every build) fails with a 500 - this
was caught and fixed during this milestone's local testing, not something
to reintroduce by "simplifying" this back to just `KnownProxies`.

The subnet is pinned explicitly (rather than trusting Docker's much wider
default bridge range, `172.16.0.0/12`) so trust is scoped to exactly this
project's own network - not every other container on this shared Plesk
host. If you ever change the compose project name or add another service
to this stack's network, keep the `networks.default.ipam` subnet and the
`KnownNetworks` value in sync.

With this correctly configured: `Request.Scheme` resolves to `https`,
Identity's `Secure` cookies are issued correctly, and password-reset/
verification links use `https://modulemint.co.uk` (from
`App__PublicBaseUrl`, never a Host header).

## Why Build & Validate is off initially

`Build & Validate` normally validates a generated plugin by installing and
activating it in a disposable WordPress container - the app calls the
`docker` CLI directly for this (`DockerPluginValidator`), which needs the
host's Docker socket mounted into the app container. That grants the app
container effective root on the host, so it is **not** enabled for this
initial production deployment: `VALIDATION_ENABLED=false` (→
`Validation:Enabled`, the same setting `ProjectsController`/
`PluginsController` already check).

With it off: standard `Build Plugin` works normally (1 credit, no Docker
involved). The `Build & Validate` button is now hidden on the Builder page
- `GET /api/credits` returns `validationEnabled: false`, and `app.js` hides
the option when that's false, rather than showing a button that would fail
every time. Attempting the underlying `POST /api/projects/build` with
`validated: true` while disabled still returns the existing clean
`ValidationUnavailable` error server-side regardless of the UI.

Local development is unaffected - `docker-compose.saas.yml`,
`docker-compose.validate.yml`, and `scripts/Validate-GeneratedPlugin.ps1`
are unrelated compose files/scripts and keep working exactly as before.

## Backups

Same three things as the general "Backup / restore" section above, with
this stack's actual volume names:

```bash
# 1. PostgreSQL - logical dump via the running container
docker exec modulemint-postgres-1 pg_dump -U modulemint -d modulemint -F c -f /tmp/modulemint-backup.dump
docker cp modulemint-postgres-1:/tmp/modulemint-backup.dump ./modulemint-backup.dump

# 2. Artifact ZIPs and 3. Data Protection keys - the named volumes
docker run --rm -v modulemint_artifacts:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/modulemint-artifacts.tar.gz -C /data .
docker run --rm -v modulemint_dpkeys:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/modulemint-dpkeys.tar.gz -C /data .
```

Back up the database and artifacts together, at roughly the same time, so a
restore never reintroduces a project/version row whose ZIP no longer
exists. No backup is sent anywhere automatically - copy these files to
wherever your own backup process/retention policy expects them. Production
secrets (`.env.production`) are not part of this - keep them backed up
separately, through whatever secure process the server administrator
already uses for credentials, never alongside application data.

## Production update

1. **Back up** (above) - non-negotiable before any update.
2. **Pull the new release** (`git pull` or however this host receives
   releases).
3. **Build the new image**: `docker compose --env-file .env.production -f docker/docker-compose.production.yml -p modulemint build`.
4. **Apply new migrations, if any** (same command as first-time setup step
   4) - before starting the new version.
5. **Start/update**: `docker compose --env-file .env.production -f docker/docker-compose.production.yml -p modulemint up -d` -
   Compose recreates only the `modulemint` service if `postgres` is
   unchanged, so there's no unnecessary database downtime.
6. **Verify** `https://modulemint.co.uk` loads.
7. **Verify login** with an existing test account.
8. **Verify OpenAI planning** (Builder → describe → Create Plan).
9. **Verify a standard plugin build/download** completes.

`scripts/Deploy-Production.sh` runs steps 2-5 plus a health-check wait, with
a confirmation prompt for step 1 - it does not perform steps 6-9, which
need a human.

## Rollback

- Keep the previous image available where practical (e.g. tag builds, or
  keep the previous git commit checked out in a separate directory) so a
  bad deploy can be redeployed quickly - `docker compose ... build` from
  the previous commit, then `up -d` again.
- Database migrations in this codebase are forward-only (see "Database
  migrations" above) - do not attempt to reverse one blindly. If a bad
  migration must be undone, restore the database backup taken in step 1 of
  the update procedure, understanding that discards any writes made since
  that backup.
- Never run `docker compose ... down -v` in production - it deletes the
  named volumes (database, artifacts, Data Protection keys) along with the
  containers. Plain `down` (no `-v`) or just recreating the `modulemint`
  service preserves all three.

## Troubleshooting

- **`docker compose up` fails immediately with a `:?` error message** - a
  required variable in `.env.production` is blank; the message names which
  one.
- **App container exits right after starting** - check
  `docker compose --env-file .env.production -f docker/docker-compose.production.yml -p modulemint logs modulemint`;
  the Production startup check (see "Required environment variables"
  above) throws a clear, non-secret error naming the category of missing
  config.
- **`https://modulemint.co.uk` doesn't load but `curl http://127.0.0.1:18473/health/ready`
  on the server does** - the problem is the Plesk reverse proxy config, not
  the app; re-check the proxy target/port and that Plesk's HTTPS
  certificate is issued.
- **Users get logged out after every deploy** - the Data Protection key
  volume (`modulemint_dpkeys`) isn't persisting; confirm it wasn't removed
  with a `down -v` and that the volume is still attached in
  `docker-compose.production.yml`.
- **Password reset / verification emails don't arrive** - check
  `RESEND_API_KEY` is a real, active key, and that this domain's DNS
  records for Resend (SPF/DKIM) are configured - that's done in your DNS
  provider, not this codebase (see "Email domain" note below).
- **`Build & Validate` doesn't appear on the Builder page** - expected with
  `VALIDATION_ENABLED=false` (see "Why Build & Validate is off" above), not
  a bug.

## Email domain (DNS)

Resend needs this domain's DNS records (SPF/DKIM, typically TXT/CNAME
entries Resend's own dashboard provides) configured for
`modulemint.co.uk` so `no-reply@modulemint.co.uk` mail is deliverable and
not marked as spam. This is a DNS change made with whoever manages
`modulemint.co.uk`'s DNS - outside this codebase and outside what an
automated deployment can do.
