# WPAIPlugin

## AI Provider API Keys

Provider API keys (Anthropic, OpenAI) are server-side configuration only.
They are never accepted from, or returned to, the browser. There is no
provider-key settings page.

**Local development** — use .NET user-secrets from `src/WPAIPlugin.Api`:
```
dotnet user-secrets set "Planning:Anthropic:ApiKey" "<your-anthropic-key>"
dotnet user-secrets set "Planning:OpenAI:ApiKey" "<your-openai-key>"
```

Equivalent environment variables also work:
```
Planning__Anthropic__ApiKey=<your-anthropic-key>
Planning__OpenAI__ApiKey=<your-openai-key>
```

**Production** — set the key via your hosting platform's own server-side
secret/environment-variable facility. No secret manager integration exists
in this codebase yet.

## Authenticated Plugin Projects (Milestone 11)

Logged-in users plan/build through the SaaS UI (`/builder.html`), and builds
are saved to their account:

- `POST /api/plugins/plan` and `POST /api/plugins/build-validated` require authentication.
- `POST /api/projects/build` (authenticated) builds, optionally validates, and
  saves a project + version 1 for the current user.
- `GET /api/projects`, `GET /api/projects/{id}`, and
  `GET /api/projects/{id}/versions/{id}/download` are authenticated and scoped
  to the current user only.

**Temporary exception:** `POST /api/plugins/build` (the original deterministic
build endpoint, no AI involved) remains unauthenticated because
`scripts/Validate-GeneratedPlugin.ps1` and the local Docker validation harness
depend on it. The SaaS browser UI no longer calls it. This exception is
intended to be removed in a later hardening milestone.

Generated ZIPs are stored on the local filesystem under
`src/WPAIPlugin.Api/App_Data/artifacts/<user-id>/<project-id>/<version-id>/plugin.zip`
(configurable via `Artifacts:RootPath`), outside `wwwroot` and never served by
static-file middleware — downloads always go through the authenticated,
ownership-checked download endpoint. That directory is gitignored.

**Apply the EF migration to your local database:**
```
dotnet ef database update --project src/WPAIPlugin.Api --startup-project src/WPAIPlugin.Api
```

## Generated Plugin Validation

Proves a plugin generated by the deterministic `PluginBuilder` can actually be
installed and activated in a real WordPress site, not just pass unit tests.

**Requires:** Docker Desktop (running), PowerShell 7+.

**Run:**

```
powershell -ExecutionPolicy Bypass -File scripts/Validate-GeneratedPlugin.ps1
```

**Expected output on success:**

```
[1/5] Starting API
[2/5] Building plugin
[3/5] Starting WordPress
[4/5] Validating plugin
[5/5] Cleaning up
PASS: Plugin installed and activated successfully.
```

**What it checks:**
- Builds and starts the existing API, POSTs a deterministic `PluginSpec`
  (exercising shortcode, custom-post-type, settings-page, custom-fields, and
  scheduled-task) to the existing `POST /api/plugins/build` endpoint
- Starts a disposable MariaDB + WordPress + WP-CLI environment via Docker Compose
- `php -l` lints every generated PHP file before anything else runs
- Installs WordPress non-interactively, then `wp plugin install` +
  `wp plugin activate` + `wp plugin is-active` against the generated ZIP
- Fails immediately, with the exact command and exit code, if any step fails

**Cleanup:** the Docker containers, network, and volume are always torn down
(`docker compose down -v --remove-orphans`) and the API process is stopped in
a `finally` block, even if validation fails — nothing is left running.

This script is a manual/CI integration check. It requires Docker and is not
part of `dotnet test`, which remains Docker-independent.

## Manual WordPress Development Site

A persistent local WordPress install for manually testing WPAIPlugin-generated
ZIPs through the real wp-admin UI. Separate from, and independent of, the
disposable validation environment above — different project name, volumes,
and port. No WordPress setup or plugin installation is automated.

**Start:**
```
.\scripts\Start-WordPressDev.ps1
```

**Open:**
```
http://127.0.0.1:18437
```

**Stop** (preserves the site):
```
.\scripts\Stop-WordPressDev.ps1
```

**Reset completely** (run manually — deletes the database and all files):
```
docker compose -f docker/docker-compose.dev.yml down -v
```
WARNING: This completely deletes the local WordPress site and database.

**Manual plugin installation:**
1. Build/download a ZIP from WPAIPlugin (`Build Plugin` in the UI, or `POST /api/plugins/build`).
2. In WordPress: **Plugins → Add Plugin**.
3. **Upload Plugin**.
4. Select the ZIP.
5. **Install Now**.
6. **Activate**.


## Credit System (Milestone 12)

Authenticated customer builds use `POST /api/projects/build`. Costs come only
from server configuration: `Credits:SignupGrant = 100`, `StandardBuildCost = 1`,
`ValidatedBuildCost = 2`. Planning costs zero. Unknown client cost fields are
ignored. `GET /api/credits` returns only the signed-in user's balance and the
two configured costs; there is no credit modification or history endpoint.

New registration creates Identity user, credit account and signup ledger entry
in one PostgreSQL transaction. The one-time `BackfillCreditsForExistingUsers`
migration grants 100 to existing users with no account. It never overwrites
existing accounts. Runtime missing-account reads return zero and never grant
credits. No credit fields were added to Identity, projects or versions.

`CreditAccounts.Version` is an application-managed concurrency token with three
attempts. Each balance change and matching immutable ledger entry share a
SaveChanges unit. Refund retries recheck existing refunds and the original
charge. Refunds use a request-independent token, and failed pending project
writes are cleared first. A committed saved build remains charged even if the
client disconnects afterward. Refund exhaustion is an error, never silent success.
A process crash or database outage during compensation requires operational
reconciliation; durable background recovery is not implemented here.

The dashboard and builder fetch authoritative balances; JavaScript never
subtracts credits locally. Build labels use server costs, and balances refresh
after build/refund. No purchase controls or payment tables were introduced.

`POST /api/plugins/build` remains the anonymous **internal/legacy deterministic
validation path** used by `scripts/Validate-GeneratedPlugin.ps1`; it does not
consume credits. The **authenticated customer SaaS path** is
`POST /api/projects/build`. No static customer UI calls the legacy path.
The pre-existing authenticated `/api/plugins/build-validated` endpoint is also
retained for compatibility and is not used by the customer UI.

Apply migrations using the established command above, with the Development
configuration for the local database. Both pre-credit migrations are preserved.
Do not reverse a spent backfill or reset the database; prefer a forward fix.

Normal `dotnet test` requires no PostgreSQL, Docker or OpenAI. The concurrent
charge/refund tests use separate InMemory contexts and a save barrier. Because
EF InMemory 8 has no transaction rollback and otherwise inserts ledger entries
before detecting account conflicts, a test-only provider adapter orders the
account update first in the same save. Production relies on PostgreSQL's
transaction rollback and does not use that adapter.

See `MILESTONE12-COMPLETION.md` for verification evidence and manual limitations.
